# ТЗ: маркетинговые отчёты — путь клиента от рекламы до причины отказа

## 1. Цель

Владелец бизнеса должен по каждому обращению уметь ответить на три вопроса
без обращения к разработчику:

1. **Откуда пришёл клиент** — канал (Telegram/MAX/WhatsApp/сайт), источник
   CRM, конкретная реклама (кампания/объявление/ключевая фраза).
2. **Что происходило до сделки** — дошёл ли до бота, на каком шаге сценария
   отвалился, если не дошёл до заявки.
3. **Почему сделка не закрылась** (или закрылась) — причина отказа,
   сумма, окупаемость вложений в рекламу (ROI/ROMI).

Документ фиксирует, какие данные для этого уже собираются и где, какие
отчёты в `apps/dashboard` уже отвечают на эти вопросы, и что нужно доделать,
чтобы ответ давался одним отчётом, а не сведением вручную нескольких вкладок.

## 2. Путь клиента и три точки отвала

```
Реклама (показ/клик) → переход по UTM-ссылке → диалог с ботом
   → создание лида/сделки в Bitrix24 → движение по стадиям воронки
   → закрытие (won с суммой / lost с причиной)
```

Клиент может «отвалиться» на трёх разных этапах, и причина отвала в каждом
случае имеет свою природу и свой источник данных:

| Этап отвала | Что известно | Источник |
|---|---|---|
| Не дошёл до бота (увидел рекламу/кликнул, но не написал) | Только агрегированные показы/клики по кампании, без привязки к конкретному человеку | `ad_daily_stats` |
| Начал диалог с ботом, но не дошёл до заявки | Шаг сценария, на котором остановился, и причина (отказался, не указал телефон, таймаут, заблокировал бота и т.д.), с привязкой к конкретному пользователю мессенджера | `bot_funnel_user_steps` |
| Заявка/сделка создана в CRM, но не закрылась в продажу | Причина провала сделки (справочник Bitrix24) | `deals.fail_reason_id` |

## 3. Источники данных (уже реализовано)

Все таблицы — `packages/db/src/schema/*`, синхронизируются с Bitrix24 и
рекламными кабинетами фоновыми джобами (`packages/jobs`), отчёты дашборда
читают из Postgres, а не дёргают внешние API на каждый просмотр.

- **`deals`** — зеркало сделок Bitrix24 (`crm.deal`), обновляется вебхуками
  (`OnCrmDealAdd/Update/Delete`) и периодической сверкой по `DATE_MODIFY`
  (`packages/jobs/src/deals-sync.ts`). Поля, относящиеся к маркетингу:
  `source_id` (источник CRM), `utm_source/medium/campaign/content/term`
  (проставляются ботом при создании сделки), `fail_reason_id` (причина
  провала, кастомное поле Bitrix `UF_CRM_1779838990`), `status`,
  `opportunity` (сумма), `stage_id`/`category_id`.
- **`deal_dictionaries`** — человекочитаемые подписи для `source_id`,
  `category_id`, `stage_id` и причин провала (синк вместе со сделками).
- **`deal_stage_history`** — append-only история переходов сделки по
  стадиям воронки (`crm.stagehistory.list`) — на каком этапе сколько
  времени провисела сделка.
- **`bot_funnel_events` / `bot_funnel_user_steps`** — путь пользователя
  мессенджер-бота до попадания в CRM: шаг сценария, `source`/`campaign` (из
  той же UTM-метки, с которой пользователь запустил бота), и `reason` —
  причина, по которой пользователь остановился на шаге и не пошёл дальше
  (`declined`, `phone_skipped`, `phone_invalid`, `timeout`, `blocked` и
  т.д.), с уникальностью по пользователю за день.
- **`ad_daily_stats` / `ad_credentials`** — фактический расход, показы и
  клики по кампаниям Яндекс.Директ и VK Ads, синкается по OAuth-доступу к
  рекламным кабинетам клиента.
- **`marketing:costs`** (Redis, `packages/api/src/costs-store.ts`) —
  расходы на источники/кампании, которые нельзя подтянуть автоматически
  (например офлайн-реклама или каналы без API), вводятся вручную помесячно.
- **`bitrix_crm_links`** — связка диалога бота (`messenger` + `userId`) с
  контактом и сделкой, которые бот реально создал в CRM (`contactId`,
  `dealId`) — источник истины, не зависящий от настроек трекера Открытой
  линии Bitrix.
- **`client_identity_links`** — склейка нескольких мессенджер-каналов
  одного человека (если написал и в Telegram, и в MAX), выполняется
  оператором вручную из инбокса «Клиенты».

## 4. Каталог отчётов (уже в `apps/dashboard`)

| Отчёт | Роут | Вопрос клиента | Разрезы/метрики | Источник |
|---|---|---|---|---|
| Конструктор отчёта | `/builder` | Произвольный срез по любой комбинации измерений | Группировка: UTM-поля, источник CRM, воронка, стадия, причина провала, день/неделя/месяц; метрики: сделки, выиграно, суммы, конверсия; фильтры и экспорт CSV | `deals` |
| UTM-отчёт | `/utm` | По какой рекламе (кампании/объявлению/ключевой фразе) пришли сделки и деньги | Вкладки source/medium/campaign/content/term, график по числу сделок и по сумме | `deals` |
| Источники | `/sources` | Какой канал CRM (source) приносит больше сделок и денег | Разбивка по `source_id` | `deals` |
| Воронка сделок | `/funnel` | Сколько сделок доходит до каждой стадии, где теряются | Стадии по `deal_stage_history`, режимы «создано/активно/дошло» | `deals`, `deal_stage_history` |
| Воронка бота | `/bot-funnel` | На каком шаге диалога с ботом клиент ушёл и почему (до создания заявки) | Шаги сценария по мессенджеру/источнику/кампании, причины отвала, drill-down до списка конкретных пользователей (`/bot-funnel/clients`) | `bot_funnel_user_steps` |
| Реклама | `/ads` | Сколько потрачено, какие кампании активны, CTR | Дневная динамика показов/кликов/расхода по Яндекс.Директ и VK Ads | `ad_daily_stats` |
| Расходы и ROI | `/costs` | Окупается ли реклама (CPL, ROMI) | Расход (ручной ввод) сопоставляется со сделками по `utm_source`+`utm_campaign`: число сделок, CPL, выиграно, выручка, ROMI | `marketing:costs` + `deals` |

## 5. Пробел: нет сквозной карточки клиента

Технически связка уже есть (`bitrix_crm_links.dealId` соединяет диалог
бота с конкретной сделкой), но ни один существующий отчёт не сводит в одну
строку весь путь одного клиента:

> реклама/кампания → шаг бота, на котором чуть не ушёл → сделка → причина
> провала или сумма выигранной сделки

Сейчас это два независимых drill-down'а: «Воронка бота» → список клиентов
по шагу (без исхода сделки) и «Конструктор отчёта»/сделки (без пути в
боте). Свести их в один отчёт «Клиент» — это то, чего в текущей реализации
не хватает для полного ответа на вопрос заголовка задачи, и что нужно
спроектировать отдельно (карточка клиента: `bitrix_crm_links` как точка
склейки `bot_funnel_user_steps.userId/messenger` с `deals.id`).

## 6. Требования к качеству данных

- Отчёты не должны читать Bitrix24 напрямую на каждый просмотр — только
  локальные таблицы Postgres, актуализируемые фоновыми джобами (уже
  реализовано, сохранить этот принцип для новых отчётов).
- `utm_*` поля сделки заполняются один раз при создании (см.
  `packages/bot-core/src/utils/utm.ts`) — если пользователь пришёл без
  UTM-метки, поля пустые; отчёты должны явно показывать долю сделок без
  UTM, а не молча исключать их из группировки.
- Причина провала (`fail_reason_id`) заполняется оператором вручную на
  стадии «Анализ причины провала» — отчёт должен показывать долю
  проигранных сделок без указанной причины как отдельную метрику качества
  заполнения CRM, а не как «причина неизвестна = 0 записей».
- ROI/ROMI в `/costs` корректен только при ручном вводе расходов; там, где
  подключены `ad_credentials` (Яндекс.Директ/VK Ads), приоритет должен
  быть у `ad_daily_stats`, а не у ручного ввода — это нужно явно
  зафиксировать в логике сопоставления, если сейчас оба источника не
  синхронизированы между собой.

## 7. Критерии приёмки

- По любому диапазону дат клиент может получить: разбивку сделок по
  UTM-source/medium/campaign/content/term с суммами и конверсией; список
  причин потери сделок с долями; воронку бота с причинами отвала до
  заявки; ROI по кампаниям, где заведены расходы.
- По конкретному клиенту (contact/deal ID или диалогу в мессенджере) можно
  проследить: с какой рекламы пришёл → на каком шаге бота чуть не ушёл (если
  применимо) → чем закончилась сделка и почему.
- Все цифры в отчётах воспроизводимы из таблиц Postgres, перечисленных в
  разделе 3, без обращения к живому API Bitrix24 или рекламных кабинетов.
