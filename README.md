# Пси-Опора — интеграция мессенджеров с Bitrix24

Монорепозиторий (Turborepo + Bun): боты Telegram и MAX, дашборд аналитики
CRM/маркетинга и интеграция всей переписки с **Открытыми линиями Bitrix24**.

## Структура репозитория

| Путь                          | Что это                                                                 |
| ------------------------------ | ------------------------------------------------------------------------ |
| `apps/tg-bot`                 | Официальный бот Telegram (Bot API, grammy)                              |
| `apps/max-bot`                | Официальный бот MAX (Bot API, Node.js-под в k3s)                         |
| `apps/dashboard`              | Bitrix24-приложение: аналитика, рассылки, настройки интеграций          |
| `apps/bitrix-webhook`         | Приём вебхуков от Bitrix24 (ответы оператора, обновления сделок)         |
| `apps/tg-userbot-worker`      | Always-on процесс для личных номеров Telegram (см. ниже)                |
| `apps/tg-vercel-proxy`        | Reverse-прокси к api.telegram.org на Vercel — на время переезда с РФ-хостинга |
| `packages/waha`               | REST-клиент WAHA для личных номеров WhatsApp (см. ниже)                 |
| `packages/bot-core`           | Общая логика сценария ботов, CRM-хелперы (webhook-транспорт)             |
| `packages/bitrix-client`      | OAuth-клиент Bitrix24 (`resolveBitrixApi`) для методов, требующих app context |
| `packages/tg-userbot`         | MTProto-клиент (mtcute) для личных номеров Telegram                      |
| `packages/db`                 | Drizzle-схемы и запросы PostgreSQL                                       |
| `packages/telemetry`         | Отправка всех ошибок приложений в SigNoz Cloud (см. [infra/README.md](infra/README.md#ошибки-и-логи-signoz-cloud)) |
| `packages/api`                | oRPC-роутеры дашборда                                                    |

## Четыре способа завести переписку в Открытую линию Bitrix24

### 1. Официальные боты (Telegram / MAX) — Bot API

Бот отвечает только на входящие (никогда не пишет первым) и дублирует всю
переписку в одну выделенную Открытую линию, чтобы оператор видел диалог и
мог ответить прямо из Bitrix24.

Регистрация коннектора, привязка к линии и вебхук бота настраиваются
**полностью через интерфейс Bitrix24** — никаких `.env`-переменных для
line/connector ID и никакого ручного запуска скриптов из терминала.

**Как это работает:**
- Карточка «Telegram/MAX — официальный бот» в дашборде (`/settings/bot`,
  `bot-connector-card.tsx`) — кнопка «Зарегистрировать канал» вызывает
  `imconnector.register` через `b24.callMethod` прямо из iframe (гарантированный
  OAuth-контекст приложения — то, что требуют методы `imconnector.*`,
  простой входящий вебхук для них не подходит, `WRONG_AUTH_TYPE`).
- Дальше — нативно в Контакт-центре: администратор добавляет канал на нужную
  линию → Bitrix открывает наш `PLACEMENT_HANDLER`
  (`/api/bitrix/bot-connector-widget/{messenger}` → `/widget/bot-connector`) —
  окно без полей ввода, которое само:
  1. активирует линию (`imconnector.activate`, oRPC `botConnector.activate`,
     `packages/api/src/routers/bot-connector`);
  2. сохраняет `connectorId`/`openLineId` в Postgres (`bot_connectors`,
     `packages/db`) — раньше это было в `.env`;
  3. **автоматически настраивает вебхук бота** (`setMessengerWebhook`,
     `packages/jobs/src/messenger.ts`) на `TG_WEBHOOK_URL`/`MAX_WEBHOOK_URL` —
     значение используется как есть, путь `/api/webhook` должен уже быть
     частью самой переменной (см. `.env.example`); заменяет ручной запуск
     `set-webhook.ts`.
- При пересылке (`deliverMessageToOpenLine`, `packages/bot-core/src/utils/bitrix/openline.ts`)
  бот читает `connectorId`/`openLineId` из той же таблицы `bot_connectors`
  (через `@psi-opora/db/queries`, драйвер `node-postgres`), а OAuth-клиент
  для самого вызова `imconnector.send.messages` резолвится при старте бота:
  `apps/tg-bot/src/server.ts` и `apps/max-bot/src/server.ts` вызывают
  `resolveBitrixApi(env.BITRIX_MEMBER_ID)`
  (`packages/bitrix-client`) и передают его в `createBot`/`createMaxBot` как `bitrixApi`.
- Пересылка идёт **в фоне** — ответ клиенту её не ждёт
  (`createBotBackgroundQueue`, `packages/bot-core/src/utils/background-tasks.ts`):
  - сообщения одного чата уходят в линию строго по очереди, прямо из
    процесса бота;
  - если Bitrix недоступен, сообщение ставится в Hatchet (`bot-openline-retry`,
    `packages/jobs/src/bot-background.ts`) и повторяется с backoff около часа
    с тем же внешним ID и временем, что у исходной попытки;
  - создание контакта/сделки и поиск контакта по диалогу сначала дожидаются
    пересылки сообщений чата: диалог Открытой линии появляется только с
    первым пересланным сообщением, без него переписка не привяжется к карточке;
  - обогащение CRM из сообщения и триаж сообщений не по сценарию (LLM)
    выполняются в Hatchet (`bot-message-analysis`), по одной задаче на чат.

  Без `HATCHET_CLIENT_TOKEN` у бота (локальная разработка) всё это
  выполняется в самом процессе, тоже в фоне, но без повторов.
- Ответ оператора приходит в `apps/bitrix-webhook` вебхуком
  (событие `ONIMCONNECTORMESSAGEADD`) и пересылается обратно клиенту через
  Bot API (`sendMessengerMessage`, `packages/jobs`).
- **Мини-приложение MAX** (кнопка «Открыть» в чате с ботом) отдаётся тем же
  `apps/max-bot` с корня `/`: запись на консультацию, вопрос в чат, контакты.
  Как прописать URL в business.max.ru и поменять тексты —
  [docs/max-mini-app.md](docs/max-mini-app.md).
- **Wazzup на том же боте.** С 08.10.2026 MAX-бот подключён ещё и к Wazzup
  (вторая webhook-подписка `max-bot.wazzup24.com`, видна в
  `GET /subscriptions`). Wazzup на первое сообщение клиента сам заводит
  контакт и сделку в «Неразобранном», а ID клиента пишет в
  `UF_CRM_MAXID_WZ` (`UF_CRM_TELEGRAMID_WZ` — для Telegram, у него это личный
  номер). Чтобы не плодить вторую карточку, бот ищет контакт Wazzup по этому
  полю (`findWazzupClient`, `packages/bot-core/src/utils/bitrix/wazzup.ts`) и
  дописывает туда недостающие телефон, email, согласие и привязку
  мессенджера. Заявку бот пишет в открытую сделку Wazzup: стадию,
  ответственного и заметки менеджеров не трогает, а в свою воронку
  (предзаказ книги) переносит только неразобранную сделку. Новую сделку бот
  заводит, если сделки Wazzup нет, она закрыта, её уже заняла прошлая заявка
  (строка «Бот:» в комментарии) или менеджер ведёт её по другому продукту.
  Без Wazzup на портале всё работает по-старому.

**Настройка:**
1. Установите приложение дашборда (`apps/dashboard`) на портал Bitrix24 —
   `DASHBOARD_BITRIX_CLIENT_ID`/`DASHBOARD_BITRIX_CLIENT_SECRET`.
2. Откройте дашборд внутри портала — рядом с карточкой «Вкладка Мессенджер»
   (`/settings/bot`) появится `memberId` портала. Впишите его в
   `BITRIX_MEMBER_ID` в `.env`.
3. Задайте `TG_WEBHOOK_URL`/`MAX_WEBHOOK_URL` **с путём `/api/webhook`**
   (например `https://your-tg-app.vercel.app/api/webhook`) — код использует
   значение как есть и путь сам не достраивает; сами токены ботов в `.env`
   не задаются.
4. Задайте `NEXT_PUBLIC_BITRIX_WEBHOOK_APP_URL` **с путём `/api/bitrix-webhook`**
   (например `https://your-bitrix-webhook.vercel.app/api/bitrix-webhook`) —
   адрес обработчика `apps/bitrix-webhook`, а не просто домен. Нужен, чтобы
   дашборд сам подписался на события коннектора при регистрации (см. шаг 5)
   — без него придётся настраивать шаг 6 руками. Если указать голый домен
   без пути, `event.bind` всё равно отработает успешно (Bitrix не проверяет
   URL при подписке), но реальные события будут улетать на 404 и до
   `apps/bitrix-webhook` не долетят.
5. В дашборде (`/settings/bot`) нажмите «Зарегистрировать канал» в карточке
   нужного бота — помимо `imconnector.register` дашборд сразу вызовет
   `event.bind` на `OnImConnectorMessageAdd`, `OnImConnectorStatusDelete` и
   `OnImConnectorLineDelete` (см. `apps/dashboard/src/lib/bitrix/connector-events.ts`),
   иначе ответы оператора не долетят обратно, а запись в `bot_connectors` не
   подчистится сама при отключении канала прямо в Bitrix. Если подписка не
   удалась — появится тост с ошибкой; Bitrix пришлёт события с собственным
   `application_token` приложения — возьмите его из первого лога
   `apps/bitrix-webhook` (`неверный токен: получено=...`) и допишите через
   запятую в `BITRIX_WEBHOOK_TOKEN`.
6. В Bitrix24: Контакт-центр → выбранная линия → каналы → добавить
   зарегистрированный коннектор — откроется наше окно активации; если токен
   бота ещё не сохранён в БД, окно попросит его ввести (@BotFather для
   Telegram или платформа MAX). Линия активируется и вебхук настроится
   автоматически (карточка в дашборде покажет статус).
7. Без дашборда (`NEXT_PUBLIC_BITRIX_WEBHOOK_APP_URL` не задан) — в
   настройках исходящего вебхука Bitrix24 (Разработчикам → Другое →
   Исходящий вебхук) отметьте события `OnImConnectorMessageAdd`,
   `OnImConnectorStatusDelete` и `OnImConnectorLineDelete` вручную и укажите
   URL `apps/bitrix-webhook` с путём `/api/bitrix-webhook`.

### 2. Личный номер Telegram (MTProto, `packages/tg-userbot`)

Отдельный коннектор Открытых линий: реальный номер телефона (не бот) — можно
писать клиенту первым и работать в групповых чатах. Поддерживает несколько
подключённых номеров одновременно, каждый — на своей линии.

**Как это работает:**
- `packages/tg-userbot` — обёртка над **mtcute** (MTProto-клиент, тот же
  протокол, что у Telegram Desktop/Web). Официального Bot API для этого
  недостаточно — только пользовательский протокол.
- Регистрация коннектора (`imconnector.register`, один раз на портал) —
  кнопка «Зарегистрировать канал» в дашборде (`/settings/bot`, карточка
  «Telegram — личный номер»), вызывается из iframe (`b24.callMethod`),
  поэтому автоматически в OAuth-контексте приложения.
- Подключение конкретного номера к конкретной линии — нативно в Bitrix24:
  Контакт-центр → добавить канал на линии → выбрать «Telegram (личный
  номер)». Bitrix откроет наш `PLACEMENT_HANDLER`
  (`/api/bitrix/tg-personal-widget` → `/widget/tg-personal-connector`) —
  узкое окно (~204px), в нём вводятся `api_id`/`api_hash` приложения
  Telegram (my.telegram.org/apps, ссылка и инструкция — во всплывающей
  подсказке `?`) и номер телефона, затем код из Telegram/SMS и, если
  включена, пароль двухфакторной аутентификации.
- Сессия MTProto и `api_hash` хранятся в Postgres зашифрованными
  (AES-256-GCM, `packages/tg-userbot/src/crypto.ts`, ключ — `TG_USERBOT_ENCRYPTION_KEY`).
  Промежуточное состояние логина (до подтверждения кода/пароля) — только в
  Redis, с TTL 10 минут.
- **`apps/tg-userbot-worker`** — единственный компонент, которому
  нужно постоянное соединение (как у настоящего Telegram-клиента), поэтому
  он не деплоится как serverless-функция, а работает как отдельный
  always-on процесс: при старте (и каждые 60 сек. после — чтобы подхватывать
  вновь подключённые номера без перезапуска) поднимает MTProto-клиент для
  каждого подключённого номера, пересылает входящие сообщения в Открытую
  линию через `imconnector.send.messages` и раз в 3 секунды вычитывает
  очередь исходящих (Redis, `packages/tg-userbot/src/outbox.ts`) — ответы
  оператора, положенные туда `apps/bitrix-webhook`.

**Настройка:**
1. Задайте `TG_USERBOT_ENCRYPTION_KEY` (32 байта base64: `openssl rand -base64 32`)
   и, при желании, `TG_USERBOT_CONNECTOR_ID` (по умолчанию `psiopora_tg_personal`).
2. `api_id`/`api_hash` **не задаются в `.env`** — их вводит администратор
   отдельно для каждого подключаемого номера прямо в виджете (см. выше).
3. Откройте дашборд внутри портала → `/settings/bot` → нажмите
   «Зарегистрировать канал» в карточке «Telegram — личный номер».
4. В Bitrix24: Контакт-центр → Открытые линии → выбранная линия → каналы →
   добавить «Telegram (личный номер)» → пройти вход (телефон → код → пароль
   при необходимости).
5. Разверните `apps/tg-userbot-worker` — единственный компонент этой
   системы, для которого нужен свой сервер (не Vercel):
   ```bash
   docker compose up -d --build tg-userbot-worker
   ```
   Ему нужны те же переменные, что и остальным приложениям: `POSTGRES_URL`,
   `REDIS_URL`, `DASHBOARD_BITRIX_CLIENT_ID`/`SECRET`,
   `TG_USERBOT_ENCRYPTION_KEY` (все — из общего `.env`).

### 3. Личный номер MAX (`packages/max-userbot`)

Неофициальный клиент пользовательского протокола MAX/OneMe: вход по номеру
телефона, коду и, если на аккаунте включён, облачному паролю (2FA);
отдельный коннектор Открытых линий на каждый аккаунт. Сессия хранится в
`max_personal_accounts` зашифрованной общим `TG_USERBOT_ENCRYPTION_KEY`.

Весь вход идёт на одном TLS-соединении: MAX привязывает токен кода и
`trackId` пароля к соединению, на котором их выдал, и на новом соединении
отвечает `service.unavailable`. Поэтому соединение входа держит
`max-userbot-worker`, а дашборд передаёт ему шаги через Redis
(`packages/max-userbot/src/login-broker.ts`); незавершённый вход живёт
10 минут и теряется при рестарте воркера. **Без запущенного воркера
подключить номер нельзя.** Версия Android-клиента, которой представляется
бот, зашита в `MAX_CLIENT_BUILD` вместе с дайджестами APK для поля `mode`
и меняется только вместе с ними — иначе MAX принимает запрос кода, но код
не отправляет.

`apps/max-userbot-worker` держит TLS-соединения с `api2.oneme.ru`, пересылает
входящие сообщения в Bitrix24 и отправляет ответы операторов из Redis-очереди.
Протокол использует MessagePack и raw LZ4 block; оба формата разбираются в
`packages/max-userbot/src/protocol`.

**Настройка:**
1. Задайте `TG_USERBOT_ENCRYPTION_KEY` и при желании
   `MAX_USERBOT_CONNECTOR_ID` (по умолчанию `psiopora_max_personal`).
2. В карточке «MAX — личный номер» зарегистрируйте слот, добавьте его на
   линию в Контакт-центре и пройдите вход «телефон → код → облачный пароль (если включён)». Воркер
   (шаг 3) к этому моменту должен быть запущен.
3. Примените миграции и запустите воркер:
   ```bash
   cd packages/db && bun run migrate
   docker compose up -d --build max-userbot-worker
   ```

Пошаговая инструкция для администратора портала —
[docs/connect-personal-max-whatsapp.md](docs/connect-personal-max-whatsapp.md).

Протокол MAX не документирован официально и может измениться без обратной
совместимости. «Написать первым» по телефону используется только рассылкой по
списку (см. «Рассылка по списку контактов»): контакт ищется по номеру
(`CONTACT_INFO_BY_PHONE`), а ID личного чата вычисляется как XOR своего и его
userId — так делает PyMax (`get_chat_id`), отдельного `CHAT_CREATE` не нужно.
Свой userId берётся из `profile.contact.id` ответа `LOGIN`. На живом аккаунте
это ещё не проверено — если не сработает, рассылка просто перейдёт к Telegram.

### 4. Личный номер WhatsApp (WAHA, `packages/waha`)

Аналог личного Telegram-номера, но постоянное соединение с WhatsApp держит
не наш процесс, а готовый self-hosted контейнер **WAHA**
(https://waha.devlike.pro, движок NOWEB = Baileys). Наш код ходит в него
обычным REST — поэтому и oRPC-роутеры дашборда, и serverless
`apps/bitrix-webhook` работают с номером синхронно, без Redis-очереди.

**Как это работает:**
- Регистрация коннектора (`imconnector.register`, один раз на портал) —
  кнопка «Зарегистрировать канал» в карточке «WhatsApp — личный номер».
- Подключение номера — нативно в Bitrix24: Контакт-центр → добавить канал
  на линии → «WhatsApp (личный номер)» → наш виджет
  (`/widget/wa-personal-connector`): телефон → pairing code, который
  вводится на самом телефоне (WhatsApp → Связанные устройства →
  Привязка по номеру телефона). Кодов из SMS и 2FA-паролей нет.
- Имя WAHA-сессии детерминировано (`waSessionName`), промежуточное
  состояние логина живёт в самой WAHA — Redis не используется. Виджет
  опрашивает `whatsappPersonal.pollStatus`, и при статусе `WORKING`
  аккаунт сохраняется в `whatsapp_personal_accounts` + `imconnector.activate`.
- Входящие: WAHA сама доставляет событие `message` вебхуком (per-session
  конфигурация, HMAC-подпись) на `apps/bitrix-webhook/api/waha-webhook`,
  который пересылает его в линию через `imconnector.send.messages`
  (`user.phone` из jid — чтобы CRM-трекер привязал существующий контакт).
- Ответ оператора: `apps/bitrix-webhook` определяет по `CONNECTOR`, что это
  WhatsApp-линия, и синхронно вызывает `POST /api/sendText` WAHA.

**Настройка:**
1. Поднимите контейнер (тот же сервер, что и `tg-userbot-worker`):
   ```bash
   docker compose up -d waha
   ```
2. Заполните в `.env`: `WAHA_URL` (для запуска вне Docker/k3s —
   доступный публичный адрес; внутри сети манифесты используют
   `http://waha:3000`),
   `WAHA_API_KEY`, `WAHA_WEBHOOK_URL` (адрес `apps/bitrix-webhook` +
   `/api/waha-webhook`), `WAHA_WEBHOOK_SECRET`.
3. В дашборде → «Каналы ботов» → «WhatsApp — личный номер» → «Зарегистрировать канал».
4. В Bitrix24: Контакт-центр → линия → каналы → «WhatsApp (личный номер)» →
   ввести телефон → ввести pairing code на телефоне.

Пошаговая инструкция для администратора портала —
[docs/connect-personal-max-whatsapp.md](docs/connect-personal-max-whatsapp.md).

⚠️ Как и у всех неофициальных интеграций WhatsApp (Baileys/whatsmeow,
Wazzup и т.п.), есть риск блокировки номера со стороны WhatsApp — не
использовать для массовых рассылок, только для диалогов с клиентами.

### 5. Отправка сообщения из карточки CRM

Вкладка «Мессенджер» в карточке сделки/контакта (`placement.bind`,
`CrmWidgetsCard`) — менеджер видит историю переписки и может написать
клиенту первым через официального бота (Telegram/MAX), если клиент уже
писал боту хотя бы раз (ограничение платформ мессенджеров: бот не может
инициировать диалог с пользователем, который никогда с ним не общался).
Канал определяется автоматически по полю «Мессенджер» контакта.

### 6. Каналы для отправки сообщений CRM (провайдеры `messageservice`)

Коннекторы Открытых линий (`imconnector.register`, разделы 1–4) видны
только в Контакт-центре. В список CRM → «Каналы для отправки сообщений»
(`/crm/messagesender/connections/`), в «Написать клиенту» в карточке и в
роботы «Отправить SMS» приложение попадает иначе — как провайдер сообщений
(`messageservice.sender.add`, тип `SMS`). Так же туда попадает и Wazzup.

**Как это работает:**
- Карточка «Каналы для отправки сообщений из CRM» в дашборде
  (`/settings/bot`, `message-sender-card.tsx`) регистрирует двух
  провайдеров: `psiopora_wa_personal` (WhatsApp, личный номер) и
  `psiopora_tg_personal` (Telegram, личный номер). HANDLER —
  `/api/message-sender` приложения `apps/bitrix-webhook` (домен берётся из
  `NEXT_PUBLIC_BITRIX_WEBHOOK_APP_URL`).
- Bitrix шлёт в HANDLER номер получателя и текст
  (`apps/bitrix-webhook/src/message-sender.ts`). Токен
  `auth[application_token]` проверяется так же, как у CRM-вебхуков
  (`BITRIX_WEBHOOK_TOKEN`). Сообщение уходит с подключённого личного номера:
  если номеров несколько — с того, с которого уже шла переписка с этим
  клиентом, иначе с первого подключённого. Повторная доставка того же
  `message_id` отсекается через Redis.
- Статус возвращается в Bitrix через `messageservice.message.status.update`
  (`sent`/`failed`, для WhatsApp — `delivered` по ack WAHA). Сообщение
  пишется в `bot_messages` (видно в инбоксе и во вкладке «Мессенджер»), а
  контакт из привязок CRM сразу связывается с клиентом — ответ клиента
  придёт в Открытую линию этого номера и откроется в той же карточке.
- Официальных ботов и личный MAX здесь нет: бот не может написать первым по
  номеру телефона, а для MAX нет подтверждённого способа открыть диалог по
  номеру (см. «Известные ограничения»).

**Настройка:**
1. В настройках локального приложения дашборда в Bitrix24 добавьте право
   **`messageservice`** и переустановите приложение (без него
   `messageservice.*` вернёт `insufficient_scope`).
2. Подключите личные номера WhatsApp/Telegram (разделы 2 и 4).
3. В дашборде нажмите «Добавить в CRM» в карточке «Каналы для отправки
   сообщений из CRM» — каналы появятся в CRM → «Каналы для отправки
   сообщений». Если домен `apps/bitrix-webhook` сменился, нажмите
   «Обновить каналы».

## Яндекс.Метрика: офлайн-конверсия «Запись на консультацию»

«Запись на консультацию» в этом продукте — это не HTML-форма на сайте, а
завершённый флоу `consult` в боте (Telegram/MAX): клиент кликает кнопку на
сайте → открывается бот → отвечает на несколько вопросов → бот создаёт
сделку в Bitrix (`submitConsultationDeal`,
`packages/bot-core/src/utils/consultation-deal.ts`). Именно в этот момент —
сразу после успешного `crm.deal.add` — отправляется офлайн-конверсия в
Яндекс.Метрику через `POST /management/v1/counter/{id}/offline_conversions/upload`
(`packages/bot-core/src/utils/yandex-metrika.ts`), без ручного экспорта из
Bitrix и загрузки в Метрику.

**Путь данных:** реклама → клик по кнопке на сайте → `ym(id,'getClientID')`
→ диплинк на бота с ClientID в `/start` → бот сохраняет ClientID в сессии →
клиент отвечает на вопросы флоу `consult` → сделка в Bitrix → офлайн-конверсия
в Метрику по этому ClientID → конверсия в отчётах Метрики привязана к
исходному визиту/кампании.

**Что нужно на сайте (вне этого репозитория)** — при клике по кнопке
«Записаться на консультацию» получить ClientID и приклеить его суффиксом
`_ymCLIENTID` к обычной ссылке на бота (`buildStartLink`/`buildMaxStartLink`,
`packages/bot-core/src/utils/utm.ts`):

```js
ym(COUNTER_ID, "getClientID", function (clientID) {
	location.href =
		"https://t.me/psiopora_bot?start=search_anorexia_708811857_ym" + clientID;
});
```

Бот отрезает суффикс до разбора кода площадки/кампании
(`extractYmClientId`) — существующие ссылки без ClientID продолжают
работать как раньше, просто без отправки конверсии.

**Настройка (всё — в дашборде, без `.env` и без деплоя):**
1. В Метрике для сайта создайте цель «JavaScript-событие» с условием
   «содержит» и идентификатором `free_free_consultation_booked` (или своим — тогда
   впишите его в поле «Идентификатор цели» на шаге 3).
2. Получите OAuth-токен с доступом к Метрике:
   https://oauth.yandex.ru/ → создайте приложение с правами на Метрику.
3. В дашборде откройте `/settings/metrika` («Яндекс.Метрика» в меню
   «Настройки») и заполните номер счётчика, OAuth-токен и идентификатор
   цели. Настройки хранятся в БД (`yandex_metrika_settings`) и подхватываются
   ботом сразу, без перезапуска.
4. (Необязательно) заведите в Bitrix пользовательское строковое поле сделки
   для ClientID и укажите его код (`UF_CRM_...`) в том же разделе дашборда —
   тогда ClientID будет виден и в самой карточке сделки, не только в
   Метрике.
5. На сайте пропишите получение ClientID и приклейку суффикса к ссылкам на
   бота, как показано выше.

**Тест по цепочке до продакшена:**
1. Открыть сайт по рекламной ссылке/UTM-метке.
2. В консоли браузера проверить, что `ym(id,'getClientID', …)` отдаёт
   значение (счётчик Метрики должен быть уже загружен к моменту клика).
3. Кликнуть «Записаться на консультацию», пройти флоу бота до конца.
4. В Bitrix — убедиться, что сделка создалась и (если в `/settings/metrika`
   указано поле ClientID) в ней есть ClientID.
5. В логах бота — найти `yandex_metrika.goal_sent` с тем же ClientID и
   `dealId` (или `yandex_metrika.upload_failed`/`upload_error`/
   `yandex_metrika.not_configured`, если что-то пошло не так).
6. В Метрике → Отчёты → Конверсии — убедиться, что цель
   `free_consultation_booked` засчиталась (данные появляются в течение ~2 часов
   после загрузки — это официальный SLA метода `offline_conversions/upload`).
7. В том же отчёте проверить, что конверсия привязалась к исходному визиту
   (источник/кампания совпадают с рекламной ссылкой из шага 1).

## Касания с рекламой: кампания, объявление, ключ — прямо в сделке Bitrix

Метка в start-параметре бота (`SITE_CODES`) — это одно значение на кнопку
сайта, и start-параметр мессенджера ограничен 64 символами. Поэтому сами
касания с рекламой едут на сервер отдельно, а с ботом их связывает тот же
ClientID Метрики (`_ym…` в ссылке, см. выше).

**Путь данных:** клик по объявлению Директа → заход на сайт с
`utm_*`/`yclid`/макросами → скрипт на сайте шлёт касание на
`POST /api/track-touch` (`apps/bitrix-webhook`, таблица `ad_touches`) →
клиент переходит в бота → при создании сделки бот по ClientID/yclid
достаёт касания за 30 дней (`packages/bot-core/src/utils/attribution`) →
сделка в Bitrix:

- `UTM_SOURCE/MEDIUM/CAMPAIGN/TERM` — с **последнего** касания.
  `UTM_CAMPAIGN` остаётся исходной меткой (дашборд сопоставляет расход Директа
  по числовому ID в её конце), `UTM_CONTENT` — заголовок объявления и его ID.
- «Источник: дополнительно» (`SOURCE_DESCRIPTION`) — читаемо:
  `Яндекс.Директ · РК «…» · группа «…» · объявление «…» (ID) · ключ «…»`.
- Комментарий в таймлайне сделки — вся цепочка касаний с датами (МСК) и
  страницами захода; в поле «Комментарий» — первое и последнее касание.
- Снимок касаний сделки — в `deal_touches` (роли first/middle/last) для
  отчётов по касаниям.
- Отдельные поля сделки (необязательно): кампания, группа, объявление,
  поисковый запрос, регион, позиция клика, страница перехода — по последнему
  касанию. Поля создаются в Bitrix как строковые, их коды задаются в
  `/settings/metrika`, карточка «Данные рекламы в сделке» (колонка
  `yandex_metrika_settings.bitrix_ad_deal_fields`); незаполненные бот не пишет.
  Регион, позиция и устройство также пишутся в таймлайн у каждого касания.
- **Поисковый запрос** приходит позже, чем создаётся сделка. Макроса с запросом
  у Директа нет, а Метрика скрывает поисковые фразы, если в выборке меньше
  10 посетителей, то есть по ClientID одного клиента запрос не получить. Поэтому
  при создании сделки клик с поиска (не РСЯ) ставится в очередь
  `ad_search_query_lookups`, и крон `ads-sync` (раз в 6 часов) после 06:00 МСК
  следующего дня ищет его в отчёте Директа `SEARCH_QUERY_PERFORMANCE_REPORT`:
  тот же день, группа, объявление (и ключ, если совпадает), есть клики. Если
  подходит один запрос — пишется он, если несколько — «вероятно: …» с самыми
  кликабельными. Запрос уходит в поле сделки и в таймлайн. Если за 3 дня после
  дня клика запрос в отчёте не появился, поиск прекращается (`not_found`).
  Для сделок с ClientID при настроенной Метрике запрос пишет только
  `metrikaVisits` по выбранному визиту из Logs API (см. ниже); очередь касаний
  такие сделки не обрабатывает.

Названия кампаний/групп/объявлений/ключей бот берёт из API Директа
(`ad_entities`, кэш 7 дней; те же учётные данные, что в `/settings/ads`) —
при создании сделки и кроном `ads-sync`. Если Директ недоступен,
в описании остаются ID, сделка создаётся как обычно. Клиенты без касаний
(нет скрипта на сайте, не по рекламе) обрабатываются по старой схеме.

**Шаблон отслеживания в Директе** (кампания → «Параметры URL», макросы
подставляет сам Директ; `yclid` добавится автоматически, если включена
разметка ссылок):

```
utm_source=yandex&utm_medium=cpc&utm_campaign={campaign_id}&utm_content={ad_id}&utm_term={keyword}&gbid={gbid}&phrase_id={phrase_id}&region_name={region_name}&region_id={region_id}&position={position}&position_type={position_type}&source_type={source_type}&device_type={device_type}
```

`region_*` — регион показа, `position`/`position_type` — место объявления в
блоке выдачи (`premium`, `dynamic_places`, `other`; `0`/`none` — показ в
сетях), `source_type` — `search` или `context`, `device_type` — устройство.
Без `gbid` не будет группы и поискового запроса.

Если нужна читаемая метка, пишите `utm_campaign=search_anorexia_{campaign_id}` —
ID кампании берётся из числового хвоста метки.

**Скрипт на сайте (вне этого репозитория)** — на каждой странице, после
загрузки счётчика Метрики:

```js
(function () {
	var p = new URLSearchParams(location.search);
	var keys = ["yclid", "utm_source", "utm_medium", "utm_campaign",
		"utm_content", "utm_term", "campaign_id", "gbid", "ad_id", "phrase_id",
		"region_name", "region_id", "position", "position_type", "source_type",
		"device_type"];
	var payload = {};
	keys.forEach(function (k) { if (p.get(k)) payload[k] = p.get(k); });
	if (!payload.yclid && !payload.utm_source && !payload.utm_campaign) return;
	ym(COUNTER_ID, "getClientID", function (clientID) {
		payload.clientId = clientID;
		payload.landingUrl = location.href.split("#")[0];
		payload.referrer = document.referrer;
		// text/plain — «простой» CORS-запрос без preflight
		navigator.sendBeacon(
			"https://<домен apps/bitrix-webhook>/api/track-touch",
			new Blob([JSON.stringify(payload)], { type: "text/plain" }),
		);
	});
})();
```

Эндпоинт открыт всем, поэтому: принимает только `Origin` из
`TRACKING_ALLOWED_ORIGINS` (по умолчанию `psi-opora.ru`), тело ≤ 4 КБ, до 60
запросов/мин с IP, значения валидируются и обрезаются, повторный заход с теми
же метками за 30 минут не плодит касание. Всегда отвечает 204 без тела.

**Тестирование:**
- Автотесты: `bun test` в `packages/bot-core` и `apps/bitrix-webhook` (логика,
  Директ и Bitrix подменены). Сквозные тесты на реальном Postgres —
  `AD_TOUCHES_TEST_DATABASE_URL=… bun test ad-touches.integration` в
  `packages/db` и `ATTRIBUTION_TEST_DATABASE_URL=… bun test
  attribution.integration` в `packages/bot-core` (БД с применёнными
  миграциями; без переменной пропускаются).
- Вручную на стенде: отправить касание —
  `curl -i -X POST https://<домен>/api/track-touch -d '{"clientId":"163972457524306386","utm_source":"yandex","utm_medium":"cpc","utm_campaign":"search_anorexia_708811857","utm_content":"<реальный ad_id>","gbid":"<реальный gbid>"}'`
  (ожидается `204`, строка в `ad_touches`); открыть бота ссылкой
  `…?start=<код>_ym163972457524306386`, пройти флоу `consult` — в сделке
  должны появиться UTM, «Источник: дополнительно» и комментарий в таймлайне.

### Реклама и визиты на сайт в сделке (Logs API Метрики, без касаний)

Основной путь данных о рекламе в сделку — фоновый, по ClientID сделки, без
скрипта касаний на сайте (касания из раздела выше необязательны). На следующий
день после создания сделки шаг `metrikaVisits` крона `ads-sync`
(`packages/jobs/src/metrika-visits`) дописывает в сделку:

- **рекламные поля** (карточка «Данные рекламы в сделке», колонка
  `bitrix_ad_deal_fields`) — по последнему визиту клиента с клика по Директу
  до заявки: кампания, группа, объявление (названия и ID Метрика отдаёт сама —
  `lastDirectClickOrderName`, `lastClickBannerGroupName`,
  `lastDirectClickBannerName`), регион — город, где был клиент
  (`regionCity`), позиция клика и регион показа — из адреса входа (`startURL`
  хранит полный адрес, поэтому в шаблоне Директа должны быть
  `position={position}&position_type={position_type}&region_name={region_name}`;
  регион показа читается и из `region=`),
  страница перехода — адрес входа без параметров, поисковый запрос — из отчёта
  Директа `SEARCH_QUERY_PERFORMANCE_REPORT` за день клика по группе/объявлению
  (один запрос — он, несколько — «вероятно: …»; для кликов в сетях не ищется);
- **поля визитов** (карточка «Визиты на сайт в сделке», колонка
  `bitrix_visit_deal_fields`): число визитов, дата первого визита и его
  источник, город и устройство последнего визита, всего страниц и времени на
  сайте, достигнутые цели;
- **UTM-поля сделки** — только если бот кампанию не знал (`UTM_CAMPAIGN`
  пустой: ссылка на бота пришла без метки, `UTM_SOURCE` = max/telegram):
  `yandex`/`cpc`, метка кампании из ссылки (иначе ID кампании), `UTM_CONTENT` и
  `UTM_TERM` из ссылки. Так сделка сопоставляется с расходом Директа в дашборде;
  настоящие метки кампаний не перезаписываются;
- в таймлайн — клик по рекламе, только если найден рекламный визит,
  поисковый запрос, только если он найден, и последние 15 визитов:
  время (МСК), источник, страницы, время, город, устройство, цели, страница входа.

Как это работает: берутся сделки с ClientID из `yandex_metrika_deal_visitors`,
не старше 14 дней, по которым сводки ещё нет; до 08:00 МСК — созданные до
вчерашнего дня, после — до сегодняшнего (к этому времени статистика за вчера
полная и в Logs API, и в отчёте Директа). Logs API отдаёт сырые визиты без
порога «меньше 10 посетителей», но не умеет фильтровать по ClientID и не отдаёт
текущий день. Поэтому выгружается весь счётчик за 30 дней до самой старой такой
сделки и по вчера, визиты сопоставляются со сделками в памяти, а визиты
остальных посетителей не сохраняются. После скачивания запрос логов очищается
(квота 10 ГБ на счётчик). Сводка записывается один раз
(`visits_summary_status` = `done` или `no_visits`), при сбое Bitrix — повторно
в следующий прогон. `no_visits`, записанное раньше 08:00 МСК следующего после
сделки дня (статистика ещё неполная), перепроверяется следующим прогоном. При выбранном рекламном визите отсутствующие рекламные
значения очищаются, чтобы не оставались данные прежнего касания. Если запрос
поискового клика с известной группой ещё не найден (в том числе при сбое
Директа), остальные данные записываются сразу, а сделка получает статус
`pending_search_query`. Следующие прогоны дописывают только найденный запрос,
без повторной сводки визитов, пока сделка не старше 14 дней.

Нужны: ClientID в сделке (суффикс `_ym…` в ссылке на бота — без него связать
сделку с визитами нечем), счётчик и OAuth-токен из настроек Метрики, причём
**токену нужны права на чтение Метрики**, и учётные данные Директа из
`/settings/ads` для поискового запроса. Пол, возраст, интересы, платёжеспособность
и поисковые фразы по одному посетителю Метрика не отдаёт ни в одном API.

### Цели Метрики по стадиям воронки

Кроме «Записи на консультацию» (уходит в момент создания сделки; если
идентификатор цели в настройках пустой — не уходит), владелец
портала может привязать любое число целей к стадиям воронок Bitrix — в
`/settings/metrika`, карточка «Цели по стадиям воронки»: название, идентификатор
цели в Метрике (цель «JavaScript-событие», создаётся в счётчике заранее) и
воронка → стадия из выпадающего списка. Счётчик и OAuth-токен общие, из
настроек выше. Таблицы: `yandex_metrika_stage_goals` (цели),
`yandex_metrika_deal_visitors` (ClientID/yclid сделки), `yandex_metrika_goal_events`
(журнал отправленного).

**Как срабатывает:** `apps/bitrix-webhook` получает `ONCRMDEALUPDATE`, и
`handleYandexMetrikaStageGoals` (`packages/jobs/src/yandex-metrika-stage-goals.ts`)
смотрит, есть ли включённые цели на текущей стадии/воронке сделки. Если есть —
в Метрику уходит офлайн-конверсия по ClientID (или `yclid`) сделки.

- **Один раз на пару «цель + сделка»**: возврат сделки в ту же стадию цель не
  дублирует. Если отправка не удалась, запись снимается и следующее изменение
  сделки повторит попытку. После сбоя воркера резерв `pending` можно занять
  повторно через 5 минут; записи `sent` повторно не отправляются.
- **Откуда берётся ClientID/yclid сделки** (по порядку):
  1. что бот запомнил при создании сделки (`yandex_metrika_deal_visitors`);
  2. пользовательское поле Bitrix (если оно указано в настройках);
  3. визит, с которым клиент открыл бота: при каждом `/start …_ym…_yc…` бот
     пишет ClientID/yclid за пользователем мессенджера
     (`yandex_metrika_messenger_visitors`), а обработчик находит его через
     IM-поле контакта сделки (Telegram/MAX ID). Так конверсия уходит и по
     сделкам, которые завёл оператор или Открытая линия, когда клиент бросил
     флоу записи. Найденный визит закрепляется за сделкой (п. 1).
     Последний визит определяется временем события `/start` (`visited_at`),
     а `updated_at` хранит время записи в БД. Для старых записей миграция
     использует прежний `updated_at` как приближение времени визита.
     Историю до появления таблицы заполняет
     `bun --env-file=.env run scripts/backfill-ym-messenger-visitors.ts --apply`
     (без `--apply` — пробный прогон).

  У сделок без ClientID/yclid (заведены вручную, клиент пришёл по ссылке без
  `_ym…`) конверсию привязать не к чему — они пропускаются
  (`yandex_metrika.stage_goal_no_visitor` в логах).
- Время конверсии берётся из `MOVED_TIME` сделки. Если оно отсутствует или
  некорректно, отправка пропускается (`yandex_metrika.stage_goal_no_stage_time`).
- Цель срабатывает на **переход** сделки в стадию (событие обновления). Если
  сделка сразу создана в этой стадии, цель не сработает — для этого есть
  «Запись на консультацию».
- Метрика принимает офлайн-конверсию не позже 21 дня после визита — для
  поздних стадий загрузка может быть отклонена (`yandex_metrika.upload_failed`).

## Email-рассылки: списки, картинки, статистика по получателю

Раздел «Email-рассылка» дашборда отправляет письмо по собственному шаблону
(`/email-templates`, React Email из `packages/emails/campaign-templates`) одной
из двух аудиторий:

- **Список контактов** (`/email-lists`, таблицы `email_lists` /
  `email_list_contacts`) — адреса не из CRM. Наполняется импортом CSV (файл
  разбирается в браузере: UTF-8 или Windows-1251 из русского Excel, разделитель
  `, ; Tab |` определяется сам, колонки email/телефон/имя выбираются вручную или
  угадываются по заголовкам) или вставкой текстом. Сервер повторно проверяет
  каждый адрес; дубли внутри списка не создаются.
- **Стадия сделок CRM** — контакты сделок стадии, как и раньше.

**Картинки** загружаются в редакторе шаблона в S3 (те же креды, что «Бэкап
CRM», префикс `email/images/`) и раздаются публично через
`/api/email-image/<uuid>.<png|jpg|gif>` дашборда — почтовые клиенты получателей
загружают их по этой ссылке. WebP/SVG не принимаются (Outlook их не показывает).

**Стоп-лист** (`email_suppressions`) — глобальный: отписавшиеся, hard bounce и
жалобы на спам попадают в него автоматически и исключаются из всех рассылок
(и по спискам, и по стадиям). В каждом шаблоне есть футер со ссылкой
«Отписаться» (`{{unsubscribe_url}}`): у Rusender это персональная ссылка на
`/api/email/unsubscribe/<id получателя>` дашборда (GET — подтверждение, POST —
отписка; сканеры ссылок не отписывают), у Unisender — его `{{UnsubscribeUrl}}`.

**Статистика по каждому получателю** (доставлено, открыто, переход, bounce,
жалоба, отписка — `email_campaign_recipients` + журнал `email_events`) приходит
вебхуками провайдера в `apps/bitrix-webhook`:

| Провайдер | Адрес | Подлинность |
|---|---|---|
| Rusender | `POST /api/email-events/rusender/<секрет>` | секрет в пути (у Rusender нет подписи); создаётся кнопкой в `/settings/email` |
| Unisender | `POST /api/email-events/unisender` | поле `auth` — MD5 тела с API-ключом; подписка через `setHook` кнопкой в `/settings/email` |

Обработчик только проверяет подлинность и ставит события в Hatchet-задачу
`email-events-ingest` (Unisender считает сбоем ответ дольше 3 с). События
дедуплицируются по `(provider, external_id)`, приходят в любом порядке —
статус получателя выводится из отметок времени, а не из последнего события.
Письма Rusender сопоставляются по uuid отправки, Unisender — по `campaign_id`
+ email. Без подключённого вебхука по получателям видно только «отправлено».

Настройка на новом портале: `/settings/email` → «Статистика доставки
(вебхуки)» → для Rusender создать адрес и добавить его в кабинете Rusender
(события `external_mail.*`, включить трекинг открытий/кликов для домена); для
Unisender нажать «Подключить вебхук». Нужен `NEXT_PUBLIC_BITRIX_WEBHOOK_APP_URL`.

## Рассылка по списку контактов (боты → личные номера → email)

Раздел «Рассылка по списку» (`/outreach`) пишет контактам из списка
(`/email-lists`) в три этапа, в форме они так и показаны:
1. **Боты MAX → Telegram** — если этот номер телефона уже писал боту.
2. **Личные номера** — тем, кто не писал ботам: каналы **в заданном
   порядке** (по умолчанию MAX → Telegram → WhatsApp; любой можно поднять,
   опустить или выключить).
3. **Письмо** по выбранному шаблону — если ни один мессенджер не доставил.

Один контакт получает сообщение только по одному каналу.

**Этап 1: боты.** Bot API не умеет «написать первым», поэтому по телефону из
списка ищется ID пользователя в мессенджере
(`packages/jobs/src/outreach/bot-targets.ts`):
- контакт CRM с этим номером (`crm.duplicate.findbycomm`) → диалоги, для
  которых бот создавал этот контакт (`bitrix_crm_links`);
- IM-поля того же контакта — IMOL-запись с коннектором нашего бота
  (`bot_connectors.connector_id`) или числовой ID в поле «Мессенджер»;
- телефон, оставленный клиентом в сценарии бота (`bot_guide_deliveries`,
  `book_preorder_orders`, сравнение полных номеров с нормализацией российских
  местных форматов и сохранением международного кода).

Не нашёлся диалог, клиент удалил чат или заблокировал бота — этап 2. Таймаут
Bot API — «не подтверждено» (запрос мог дойти), как у личных номеров. У
ботов нет пауз и дневных лимитов (банят личные номера), но окно отправки
соблюдается; после каждого контакта — 1 с паузы под лимит Bitrix24 на
поиск. Отправка — `sendMessengerMessage`, в журнал `bot_messages` под
messenger `max`/`telegram`. Флаг — `outreach_campaigns.settings.useBots`; у
рассылок, созданных раньше, его нет — без ботов. Доступность каждого бота
на момент создания кампании сохраняется в `settings.bots` для отчёта.

**Настройки доставки личных номеров** (`outreach_campaigns.settings`, форма
запоминает последние настройки в браузере):
- Темп — **для каждого номера отдельно** (блокируют номер, а не рассылку):
  случайная пауза «от–до», лимит сообщений в сутки (МСК, считается по номеру
  по всем рассылкам — `getOutreachAccountUsage`, попытка «номера нет в
  мессенджере» тоже считается), перерыв после каждых N сообщений. Пресеты
  «Осторожно / Стандарт / Быстро».
- Исчерпан дневной лимит: **ждать следующих суток** (порядок каналов
  соблюдается) или **пропустить канал** — контакт идёт следующим каналом, в
  попытках канал отмечается как пропущенный (`attempts[].skipped`).
- **Окно отправки** — дни недели и часы по Москве; вне окна рассылка на паузе.
- **Не писать повторно** тем, кому рассылка по списку уже дошла за N дней
  (по телефону — «отправлено/не подтверждено», по email — «передано в email»);
  такие контакты сразу «пропущены», их число видно в предпросмотре.

**Списки без дублей.** У контакта списка есть телефон и/или email
(`email_list_contacts.phone` / `.email`, нормализованы: `+79991234567`,
lower case), оба уникальны в пределах списка (уникальные индексы
`(list_id, phone)` и `(list_id, email)`). Строка импорта, совпавшая с
контактом хотя бы по одному из них, дополняет его (имя, недостающий телефон
или email) — `planContactMerge` в `packages/db/src/queries/contact-merge.ts`.
Если строка связывает два контакта (телефон у одного, email у другого) и их
данные не противоречат, контакты склеиваются в один (атомарным SQL — удаление
и обновление одним запросом). Если противоречат (у контакта уже другой
email/телефон), строка не меняет список и показывается как конфликт.

**Каскад** (`packages/jobs/src/outreach/cascade.ts`, Hatchet-задача
`outreach-deliver`):
- MAX и Telegram — через очереди воркеров (`apps/max-userbot-worker`,
  `apps/tg-userbot-worker`) по телефону. Нет ответа воркера за 30 с — задача
  снимается из очереди (`LREM`); снялась — канал считается упавшим до конца
  запуска. Не снялась (воркер уже взял) — ждём ещё минуту, потом статус
  «не подтверждено», и каскад для этого контакта **останавливается**, чтобы не
  написать человеку дважды.
- WhatsApp — WAHA: сначала `GET /api/contacts/check-exists`, без этого
  `sendText` на номер без WhatsApp «успешно» уходит в никуда.
- Флуд-ограничения (`FLOOD_WAIT`, `PEER_FLOOD`) и отключённый номер выключают
  канал до конца запуска сразу; неответ воркера или недоступная WAHA — только
  после 3 сбоев подряд (`ChannelBreaker`), чтобы разовая задержка не ломала
  приоритет. Контакт при сбое канала идёт следующим каналом.
- Перед каждой попыткой шлюз темпа (`outreach/scheduler.ts`, правила — в
  `outreach/pacing.ts`) ждёт окно отправки и паузу номера. Короткие ожидания
  выдерживаются в запуске (с проверкой отмены), длинные (ночь, лимит до
  следующих суток, перерыв на стыке запусков) — отложенным запуском Hatchet
  (`scheduled.create`); до него в отчёте «Пауза до … — причина»
  (`resume_at` / `pause_reason`). Прерванный посреди цепочки контакт
  продолжает с того канала, где остановился. Задача работает до 50 минут и
  перезапускает сама себя — длинные списки идут часами без многочасового
  `executionTimeout`. Рассылки, созданные до появления настроек
  (`settings = null`), идут как раньше: MAX → Telegram → WhatsApp, пауза ±25%.
- Отмена рассылки на паузе сразу будит задачу, чтобы письма тем, кому
  мессенджеры не дошли, ушли без ожидания отложенного запуска.
- В конце все, кому не дошло, одной email-кампанией (`email_campaigns`,
  видна в «Email-рассылке») уходят через активного провайдера — со ссылкой
  отписки, стоп-листом и статистикой открытий. Email из стоп-листа не
  используется. Email-фаза запускается и при отмене, и при падении рассылки —
  для тех, кому мессенджеры уже не дошли. Если задачу писем поставить не
  удалось, получатели остаются «ждёт email» с причиной, а не «передано».

**Кому что ушло.** `outreach_campaigns` / `outreach_recipients`: по каждому
контакту — итог (канал или «не доставлено»/«не подтверждено»), цепочка
попыток с ошибками (`attempts`) и для писем — ссылка на строку email-кампании
(статус доставки/открытия). Отчёт — на `/outreach/<id>` с выгрузкой в CSV;
сообщения в мессенджеры пишутся и в `bot_messages` (видны в инбоксе как
исходящие рассылки, ответ клиента придёт в Открытую линию этого номера).

**Отчёт: отправитель, прочтение, ответ.** У получателя есть
`journal_message_id` — его строка в `bot_messages`. Из неё отчёт берёт:
- **отправителя** — личный номер канала из `outreach_campaigns.accounts`
  («Личный WhatsApp +7 999 …»), бота или адрес отправителя письма;
- **статус в мессенджере** (`bot_messages.status`): доставлено/прочитано.
  Источники: WhatsApp — ack-вебхук WAHA; личный Telegram —
  `updateReadHistoryOutbox` (`listenForOutboxRead` в `tg-userbot-worker`,
  отмечает исходящие до `maxReadId`); личный MAX — пуш `NOTIF_MARK`
  (opcode 130). Боты Telegram/MAX о прочтении не сообщают — в отчёте
  «мессенджер не сообщает о прочтении», а не «не прочитано»;
- **«Ответил»** — первое входящее в том же диалоге (тот же личный номер)
  после рассылки; работает для всех мессенджеров, включая ботов.

Плитки «Прочитали» / «Ответили» на `/outreach/<id>` — с фильтрами; те же
поля — в CSV. У рассылок, отправленных до появления связи, — «статус
неизвестен».

**`NOTIF_MARK` не проверен вживую.** Поля взяты из PyMax (`{chatId, userId,
mark, setAsUnread}`); прочтением считается только кадр, где есть чат,
прочитал не свой аккаунт и `mark` похож на время в мс
(`parseReadMark` в `packages/max-userbot/src/relay.ts`). Каждый кадр
`max-userbot-worker` пишет в лог (`NOTIF_MARK …`) — по нему проверить
раскладку на живом аккаунте и при необходимости поправить разбор.

**Запуск:** примените миграцию (`cd packages/db && bun run migrate`),
перезапустите `hatchet-worker` и оба userbot-воркера (в них новая обработка
отправки по телефону).

## Быстрый старт

```bash
bun install
cp .env.example .env   # заполнить по комментариям в файле
bun run dev:dashboard   # или dev:tg / dev:max — см. package.json
```

`DASHBOARD_BITRIX_WEBHOOK_URL` (входящий вебхук) — часть функций (регистрация
коннекторов, вкладки CRM) при этом недоступна, т.к. требует реального
OAuth-контекста приложения.

## Известные ограничения

- **Писать первым могут личные номера Telegram и WhatsApp**, но не
  официальные боты (Bot API принципиально не позволяет инициировать диалог).
  Личный MAX работает через неофициальный reverse-engineered протокол;
  «написать первым» по телефону сделано для рассылки по списку и для вкладки
  «Мессенджер» в карточке CRM (ID чата = XOR userId, как в PyMax) и ещё не
  проверено на живом аккаунте — при сбое рассылка переходит к следующему
  каналу, а вкладка показывает ошибку воркера. Вкладка адресует MAX по
  телефону контакта, а после отправки привязывает к контакту CRM ID личного
  чата (`bitrix_crm_links`), под которым в журнале лежит переписка. Провайдер
  `messageservice` для MAX по-прежнему пишет только в существующие чаты.
- У каждого официального бота (Telegram/MAX) — ровно один экземпляр
  (один токен), но линию для него можно переназначить в любой момент прямо
  в Контакт-центре — просто добавить канал на другой линии, без правки `.env`.
  Личные номера Telegram, WhatsApp и MAX поддерживают несколько одновременно
  подключённых аккаунтов через отдельные коннекторы.
- Предположение о формате `PLACEMENT_OPTIONS` для плейсмента настроек
  коннектора (`SETTING_CONNECTOR`) сделано по аналогии с плейсментом вкладок
  CRM — официально не задокументировано, стоит перепроверить на реальном
  портале (см. `TODO` в `apps/dashboard/src/app/api/bitrix/tg-personal-widget/route.ts`
  и `.../bot-connector-widget/[messenger]/route.ts`).
